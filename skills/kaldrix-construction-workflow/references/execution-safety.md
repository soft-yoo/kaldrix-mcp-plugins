## Execution and Safety

- Prefer read tools before write tools. Resolve exact object identifiers instead of guessing from names.
- Read `structuredContent.result` for annotation-based tool payloads. Text content may be empty.
- Read, write and delete capabilities are separate scopes. Perform a destructive operation only when the user explicitly requested it; delete tools require the delete scope and `confirm=true`.
- Messages on behalf of the company (`send_estimate_offer`, `send_project_contract`), every `update_project_estimate` call (settings, offer details, markups, status; approval also makes the estimate immutable), `generate_estimate_pdf`, overwriting existing price-list data (`import_price_list` after `dryRun`, `adjust_price_list_prices` after `dryRun`) and replacing hand-typed prices (`refresh_estimation_item_prices` with `includeOverridden`) also require `confirm=true` after an explicit user decision.
- Confirmed process decisions require their declared scope and explicit confirmation: `sign_acceptance_protocol` (`realization.write`, confirm=true), `complete_project_realization` (`realization.write`, confirm=true), `mark_project_contract_signed` (`contracts.write`, confirm=true) and `cancel_project_contract` (`contracts.delete`, confirm=true). Returning a sent contract for corrections and clearing an instalment payment need `confirm=true` too. Ask the person responsible on site or in the office before each of them.
- Restoring a project version (`restore_project_version`, `history.restore`) replaces the current model and, when chosen, the draft estimates; then every editable draft gets the model-counted quantities of the restored model. Call it with `confirm=true` only after the user approved the result of `preview_project_version`; without it the tool returns only the preview. Use one `operationId` per restore and reuse it on retry. Before a large or risky change you may save a version with `save_project_version`.
- For tools with `idempotencyKey`, generate a stable key for one intended operation and reuse it only for an identical retry. Every physical model write requires `expectedModelVersion` from the reviewed state; individual physical create/add tools require `idempotencyKey`. Estimate, price-list and quick-house keys are stored server-side for 24 hours; `IDEMPOTENCY_IN_PROGRESS` means read the state before deciding to retry.
- A failed tool call has `isError=true`; read `structuredContent.code`, `classification`, `field`, `message`, `retryable`, `nextTools` and optional `context`. Its text starts with `MCP_ERROR` and contains the same JSON.
- For `VALIDATION_FAILED`, use `field` and `context.validationRule` to correct the indicated input. Closed values (kinds, statuses, types, modes) are listed as `enum` in the input schema and are case-sensitive: send them exactly as listed. An enum failure includes `context.allowedValues`; type failures may include `context.expectedType`. Unknown fields must be removed or renamed according to the schema. The error does not echo submitted values; if a detailed hint is unavailable, inspect the tool input schema.
- Do not retry a failed mutation blindly. `retryable=true` permits retrying only after correcting the input; for `TEMPORARILY_UNAVAILABLE` retry a read unchanged after a short pause, and read current state before retrying a write. Report `callId` from the error when a failure repeats. Never infer user approval from an error or set `confirm=true` automatically. Read current state before retrying an uncertain write.
- Protocol-level failures carry correlation data too. JSON-RPC `-32603` (internal error) has `data.requestId`: retry once, and report that `requestId` if it repeats. HTTP 503 with `code=TEMPORARILY_UNAVAILABLE` and `Retry-After` means authentication or a company check could not complete; retry after the pause, without reconnecting. HTTP 401 `invalid_token` means the connection must be re-authorized.
- After a meaningful mutation, read back the smallest relevant object. For geometry, also run validation.
