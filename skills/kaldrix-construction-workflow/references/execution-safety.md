## Execution and Safety

- Read before writing; resolve exact object identifiers instead of guessing from names.
- Read `structuredContent.result` for annotation-based tool payloads; text content may be empty.
- Read, write and delete are separate scopes. Run a destructive operation only on explicit user request; delete tools need the delete scope and `confirm=true`.
- Also need `confirm=true` after an explicit user decision: messages on behalf of the company (`send_estimate_offer`, `send_project_contract`), every `update_project_estimate` call (settings, offer details, markups, status; approval also makes the estimate immutable), `generate_estimate_pdf`, overwriting price-list data (`import_price_list` after `dryRun`, `adjust_price_list_prices` after `dryRun`) and replacing hand-typed prices (`refresh_estimation_item_prices` with `includeOverridden`).
- Confirmed process decisions: `sign_acceptance_protocol` (`realization.write`, confirm=true), `complete_project_realization` (`realization.write`, confirm=true), `mark_project_contract_signed` (`contracts.write`, confirm=true) and `cancel_project_contract` (`contracts.delete`, confirm=true). Returning a sent contract for corrections and clearing an instalment payment need `confirm=true` too. Ask the person responsible on site or in the office before each.
- `restore_project_version` (`history.restore`) replaces the current model and, when chosen, the draft estimates; every editable draft then gets the restored model's counted quantities. Send `confirm=true` only after the user approved the `preview_project_version` result; without it the tool only previews. One `operationId` per restore, reused on retry. Before a large or risky change you may `save_project_version`.
- `idempotencyKey`: one stable key per intended operation, reused only for an identical retry. Every physical model write needs `expectedModelVersion` from the reviewed state; individual physical create/add tools need `idempotencyKey`. Estimate, price-list and quick-house keys are stored server-side for 24 hours; `IDEMPOTENCY_IN_PROGRESS` means read the state before deciding to retry.
- A failed call has `isError=true`; read `structuredContent.code`, `classification`, `field`, `message`, `retryable`, `nextTools` and optional `context`. Its text starts with `MCP_ERROR` and holds the same JSON.
- `VALIDATION_FAILED`: correct the input named by `field` and `context.validationRule`. Closed values (kinds, statuses, types, modes) are case-sensitive `enum` lists in the input schema; send them exactly. Enum failures include `context.allowedValues`; type failures may include `context.expectedType`. Remove or rename unknown fields per the schema. Errors do not echo submitted values; without a detailed hint, inspect the input schema.
- Never retry a failed mutation blindly: `retryable=true` allows a retry only after correcting the input. `TEMPORARILY_UNAVAILABLE`: retry a read unchanged after a short pause; read current state before retrying a write. Report the error's `callId` when a failure repeats. Never infer approval from an error or set `confirm=true` automatically. Read current state before retrying an uncertain write.
- Protocol failures: JSON-RPC `-32603` (internal error) has `data.requestId` — retry once, report that `requestId` if it repeats. HTTP 503 with `code=TEMPORARILY_UNAVAILABLE` and `Retry-After`: authentication or a company check could not complete; retry after the pause without reconnecting. HTTP 401 `invalid_token`: re-authorize the connection.
- After a meaningful mutation read back the smallest relevant object; for geometry also run validation.
